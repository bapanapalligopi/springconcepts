# Chapter 13.5 — Spring Boot Actuator Info Endpoint ⭐⭐⭐⭐

The **Health Endpoint** tells us:

> **"Is the application healthy?"**

The **Info Endpoint** tells us:

> **"What application is this?"**

It provides metadata such as:

* Application name
* Version
* Build number
* Git commit
* Environment
* Company information
* Release date

This endpoint is especially useful in **production environments** where multiple versions of an application may be deployed.

# 1. What is the Info Endpoint?

The Info Endpoint exposes **application metadata**.

URL:

```http id="prk8y7"
GET /actuator/info
```

Example response:

```json id="r5jd6v"
{
  "app": {
    "name": "Employee API",
    "version": "1.0.0"
  }
}
```

Notice:

This endpoint **does not check application health**.

It only displays information.

# 3. Default Behavior

Without configuration:

```http id="sr7nr8"
GET /actuator/info
```

Response:

```json id="6mpsuz"
{}
```

Why?

Because Spring Boot doesn't know what information you want to expose.

---

# 4. Adding Custom Information

In `application.properties`:

```properties id="n5m5ml"
info.app.name=Employee Management System
info.app.version=1.0.0
info.app.company=ABC Technologies
```

Now:

```http id="v4frna"
GET /actuator/info
```

Response:

```json id="nsl7sn"
{
  "app": {
    "name": "Employee Management System",
    "version": "1.0.0",
    "company": "ABC Technologies"
  }
}
```

Spring automatically maps all properties beginning with `info.`.

# 6. Build Information

Applications are usually built using Maven or Gradle.

During the build, we can generate metadata.

Example:

```text id="d9muhh"
Application Name

↓

Version

↓

Artifact

↓

Build Time
```

Spring Boot reads this automatically if a `build-info.properties` file is generated during the build.

Example response:

```json id="jlwm18"
{
  "build": {
    "artifact": "employee-api",
    "version": "1.2.5",
    "time": "2026-07-20T10:00:00Z"
  }
}
```

---

# 7. How Build Information Works

Build Process:

```text id="djlwm2"
Source Code

↓

Maven Build

↓

Generate build-info.properties

↓

Package Application

↓

Actuator Reads File

↓

Expose /actuator/info
```

You don't manually edit `build-info.properties`.

It is generated by the build tool.

# 14. Common Mistakes

### Mistake 1

Expecting `/actuator/info` to show build data automatically.

It won't unless build metadata is generated.

---

### Mistake 2

Putting sensitive information under:

```properties id="jlwm14"
info.*
```

Don't expose:

* Passwords
* API keys
* Tokens
* Internal secrets

---

### Mistake 3

Confusing:

```text id="jlwm15"
/actuator/info
```

with

```text id="jlwm16"
/actuator/env
```

`info` is intended for selected metadata.

`env` exposes environment configuration (and is much more sensitive).

---

# 15. Best Practices

```text id="jlwm17"
✅ Include application name

✅ Include version

✅ Include build information

✅ Include Git commit ID

✅ Include environment name if useful

❌ Don't expose secrets

❌ Don't expose internal credentials

❌ Don't overload info with unnecessary data
```

# 16. Interview Questions

### What is the purpose of `/actuator/info`?

> It exposes metadata about the application such as version, build, and Git information.

---

### What prefix is used for custom properties?

```properties id="jlwm19"
info.*
```

---

### Can build information be generated automatically?

Yes.

Using Maven or Gradle build plugins that generate `build-info.properties`.

---

### Can Git information be exposed?

Yes.

If Git metadata is generated (typically into `git.properties`), Actuator can expose it.

---

### Should secrets be stored under `info.*`?

No.

Only non-sensitive metadata should be exposed.
